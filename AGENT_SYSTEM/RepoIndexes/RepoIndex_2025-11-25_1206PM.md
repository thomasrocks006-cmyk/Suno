## 10. Architecture Patterns

### 10.1 Component Patterns

**Pattern 1: Container/Presenter**
- ResultDisplay.tsx = container
- LyricsView, AnalysisView, etc. = presenters
- Clean separation of concerns

**Pattern 2: Service Layer Abstraction**
- Components never call Gemini directly
- All AI through geminiService.ts
- All audio through sunoService.ts
- Testability and maintainability

**Pattern 3: Context for Global State**
- AudioContext for playback state
- Avoids prop drilling
- Centralized audio management

**Pattern 4: Lazy Loading**
- Heavy modals (ValidationDashboard, LearningInsightsDashboard, CostDashboard)
- Loaded on demand
- Improves initial bundle size

### 10.2 Data Flow Patterns

**Pattern 1: Generation Flow**
```
InputForm → App.tsx → generateSongAssets() → geminiService
    → Structured JSON → App state → ResultDisplay
    → Background analysis → analyzeGeneratedSong()
    → Update state → Re-render with analysis
```

**Pattern 2: Analysis Flow**
```
Song generated → agentDebateService.run5AgentAnalysisWithDebates()
    → Base analysis (3s) → 5 agents parallel (3s)
    → Calculate tradeoffs → Simulate votes (FAKE ❌)
    → Return analysis object → Update song.analysis
    → Render AnalysisView → AgentDebateModal (if clicked)
```

**Pattern 3: Rewrite Flow**
```
User clicks "Rewrite" → rewriteSongWithImprovements()
    → Gather context (scores, weaknesses, sonic)
    → Build prompt with execution plan schema
    → Call Gemini with structured output
    → Return new song with plan
    → Update history → Display LiveRewritePlan
```

### 10.3 State Management Patterns

**Pattern 1: LocalStorage Persistence**
- Song history auto-saved on change
- Cost tracking persists across sessions
- Personalization context saved
- Learning entries tracked

**Pattern 2: Optimistic Updates**
